## 2. Address map used by the backend (verified against Delta documentation)

Source: Delta **AH500 Operation Manual, Appendix B.1 "Device Addresses"** (table "Standard Modbus addresses of devices").
Implemented in `backend/app/delta_ah500.py`, unit-tested against every end point of that table (`backend/tests`).

| Device | Type | Range | Read FC | Zero-based (hex, on the wire) | One-based reference |
|---|---|---|---|---|---|
| X | Bit | X0.0~X511.15 | 02 | 6000~7FFF | 124577~132768 |
| X | Word | X0~X511 | 04 | 8000~81FF | 332769~333280 |
| Y | Bit | Y0.0~Y511.15 | 01 | A000~BFFF | 040961~049152 |
| Y | Word | Y0~Y511 | 03 | A000~A1FF | 440961~441472 |
| M | Bit | M0~M8191 | 01 | 0000~1FFF | 000001~008192 |
| SM | Bit | SM0~SM2047 | 01 | 4000~47FF | 016385~018432 |
| SR | Word | SR0~SR2047 | 03 | C000~C7FF | 449153~451200 |
| D | Word | D0~D32767 | 03 | 0000~7FFF | 400001~432768 |
| S | Bit | S0~S2047 | 01 | 5000~57FF | 020481~022528 |
| T | Bit / Word | T0~T2047 | 01 / 03 | E000~E7FF | 057345~ / 457345~ |
| C | Bit / Word | C0~C2047 | 01 / 03 | F000~F7FF | 061441~ / 461441~ |
| HC | Bit / DWord | HC0~HC63 | 01 / 03 | FC00~FC3F | 064513~ / 464513~ |
| E | Word | E0~E31 | 03 | FE00~FE1F | 465025~465056 |

Rules:

* **Zero-based vs one-based.** The backend always sends the zero-based hex address. The one-based reference is shown only
  so you can compare with HMI/SCADA tools that use 4xxxxx-style numbering.
* **Device number ≠ Modbus address.** X0.8 is not address 8. It is `0x6000 + 0×16 + 8 = 0x6008` (ref 124585).
  Y1.12 = `0xA000 + 1×16 + 12 = 0xA01C`. Only D and M start at 0.
* **Bit inside a word** (e.g. alarm bit `D15000.3`): read holding register D15000 (FC03) and take bit 3.
* **32-bit values** (REAL/DINT) use two consecutive D registers. Delta stores the **low word in the lower address**
  (D11008 = low, D11009 = high). The default word order is therefore `low_first` (CDAB). Each register's bytes are
  big-endian, as Modbus requires.
* **D range.** The manual's Modbus table covers D0~D32767. Every register used in this project is ≤ D15001.

## 4. Site verification procedure (before removing "UNVERIFIED")

1. Admin → Communication: confirm the IP the backend can reach through the IoT gateway/VPN (PLC IP, or the gateway's
   forwarded IP/port). Leave the unit ID at 1 and the port at 502.
2. Click **Test connection**. It opens TCP and reads D0 (FC03 @ 0).
3. Admin → Tags → open each tag → **Test read**. Compare the result with the DOP HMI screen or the ISPSoft device monitor.
   * For REAL tags the result also shows the value with the swapped word order. If only the swapped value matches the
     HMI, change the word order.
   * For BOOL inputs, toggle or observe the field device and check the polarity. Tick *Invert* for NC contacts if required.
4. Tick **Mapping verified on site** per tag → **Save tags**.
5. Communication → set Mode = *Modbus TCP*, tick **PLC communication verified on site**, enter your name and a note → Save.

Until steps 4–5 are done, the client dashboard labels values **UNVERIFIED**. In simulation mode it labels them **SIMULATED**.
